# Business model

jeegit is released under Apache-2.0 and intends to stay a **pure open-source** project at the
code level. The commercial surface follows the Google OSS playbook — the code is free,
differentiation is in the *service around the code*.

## Revenue paths (for downstream commercial adopters)

1. **Implementation & integration services.** Hourly / project-based work to on-board a team.
2. **Training & certification.** Operator, developer, and architect tracks mirroring the pattern
   Google Cloud uses for its OSS-adjacent stack (GKE, TensorFlow).
3. **Managed runtime.** A hosted jeegit offering with SLAs and a managed Model Gateway — the
   Apache-2.0 code is unchanged; the value is in the *operations*.
4. **Industry templates & plugins.** Community-written agents / prompt libraries / workflow
   packages. jeegit is the platform; verticals ship on top.
5. **Compliance consulting.** Configuration, DPA advisory, privacy reviews — anchored on the
   governance charters we already publish.

## Monetisation *we will not* pursue

- Shipping a "community edition" with artificial limits. The code stays single-tier.
- Proprietary plugins that gate core functions. New capabilities land in the open repo first.
- Exclusive-licence deals. If a downstream vendor needs an exclusive right, Apache-2.0 already
  permits relicensing their own extensions; we don't relicense the core.

## Why Apache-2.0

- Maximum compatibility with enterprise procurement (including the kind of public-sector RFPs
  that commonly reject copyleft).
- Patent-grant clause that lets contributors and adopters sleep at night.
- Mirrors the licence of Spring Boot, Kubernetes, Kafka, and most of the JVM stack we rely on.

## Success signals (not revenue)

- Contributors outside the founding team.
- Production deployments in at least three distinct regulatory environments.
- Downstream vendors publishing their own commercial offerings on top — we measure reach, not
  capture.

## Funding of the project itself

- Donations via GitHub Sponsors (when enabled).
- Corporate sponsorships that fund specific work packages — always in exchange for OSS
  deliverables, never in exchange for closed-source features.
- Fiscal hosting through a neutral foundation (Apache, LF, OpenJS) if and when adoption
  justifies it.
